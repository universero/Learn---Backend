## 概述

索引是帮助存储引擎快速获取数据的一种数据结构

索引的分类如下
- 按数据结构分类: B+Tree索引, Hash索引, Full-Text索引
- 按物理存储分类: 聚簇索引(主键索引), 二级索引(辅助索引)
- 按字段特性分类: 主键索引, 唯一索引, 普通索引, 前缀索引
- 按字段个数分类: 单列索引, 联合索引

InnoDB会根据不同的场景选择不同的列作为索引
- 有主键, 默认使用主键作为聚簇索引的索引键
- 没有主键, 默认选择第一个不包含NULL的唯一列作为聚簇索引
- 都没有, 则生成一共隐式自增id作为索引
其他的索引都属于二级索引, 主键索引和二级索引都默认使用B+Tree索引

## B+Tree索引的存储和查询过程

B+Tree是一个多叉树, 叶子节点才存放数据, 非叶子节点只存放索引, 而且每个节点里的数据是按主键顺序存放的. 每个父节点的索引值都会出现在下次子节点的索引值中, 因此在叶子节点中, 包含了所有的索引值信息, 并且每个叶子节点都有两个指针, 分别指向下一个叶子节点和上一个叶子节点, 形成一个双向链表.

- 主键索引
	- 在查询语句中如果使用了主键索引查询, 那么B+Tree会自顶向下逐层查找索引. 数据库的索引和数据都是存储在硬盘的, 可以把每次读取一个节点当作一个I/O操作. 千万级的数据只需要3-4层即可, 所以B+Tree相比于B树和二叉树来说, 查询效率高很多
- 二级索引
	- 二级索引的叶子节点存放的是主键值而不是实际数据. 在查询语句中如果使用了二级索引, 那么会先检索二级索引的B+Tree找到对应的叶子节点, 然后通过查询到的主键值在主键索引的B+Tree中查询到对应的叶子节点, 然后获取到整行数据. 这个过程也叫回表, 即查询两个B+Tree才能查到数据
	- 不过当查询的数据是在二级索引中的叶子节点中能查询到时(主键索引), 不会再回表, 这个过程叫做覆盖索引.

## B+树索引的优势

- 相对于B Tree
	- B+Tree只在叶子节点存储数据, 而B树的非叶子节点要存储数据, 所以相同的I/O次数下能查询更多的节点
	- B+Tree的叶子节点采用双链表链接, 适用于MySQL常见的范围查询
	- B+树有很多冗余节点, 删除时非常快速
- 相对于二叉树
	- 对于N个叶子节点的B+Tree, 搜索复杂度为O(logdN), d为节点允许的最大子节点数
	- 而二叉树是O(logN), I/O次数多很多

## 联合索引

将多个列作为索引称作联合索引.
联合索引存在最左匹配的原则, 使用联合索引时, 需要从左到右的给出索引(SQL中语序可以不对, 因为有查询优化器, 但是必须出现), 如果不符合最左匹配原则, 那么就无法使用联合索引, 利用索引的前提是索引里的key是有序的

### 联合索引范围查询

并不是查询过程中使用了联合索引查询, 就代表了联合索引中的所有字段都用到了联合索引进行索引查询, 也存在部分字段用到联合索引, 部分字段没有用到的情况, 也就是范围查询

- case1 `select * from t_table where a > 1 and b = 2`, 联合索引(a, b)
	- a>1的条件可以用联合索引快速定位到满足的第一条记录
	- 但是b=2却不行, 因为a>1时b并不是完全有序的, 所以这里就必须扫描所有的a>1的记录
- case2 `select * from t_table where a >= 1 and b = 2`, 联合索引(a, b)
	- 这和case1非常像, 只不过多了个a字段的查询条件>=
	- 由于联合索引是先按a排序然后按b排序, 所以a>=1的条件的二级索引记录肯定是相邻的, 于是可以快速定位到第一条记录, 然后按顺序扫描
	- 虽然a>=1条件中的二级索引记录的范围里, b是无序的, 但是在a=1时, b是有序的, 于是通过b=2可以减少需要扫描的记录范围, 即先找到a=1,b=1的记录作为第一条
- case3: `SELECT * FROM t_user WHERE name like 'j%' and age = 22`, 联合索引(name, age)
	- 和case2基本一致, name是有序的, name相同时age也是有序的

联合索引的最左匹配原则，在遇到范围查询（如 >、<）的时候，就会停止匹配，也就是范围查询的字段可以用到联合索引，但是在范围查询字段的后面的字段无法用到联合索引。注意，对于 >=、<=、BETWEEN、like 前缀匹配的范围查询，并不会停止匹配

### 索引下推

在找到联合索引后的第一个满足条件的主键后, 还需要判断其他条件是否满足, 如第二个联合索引, 那这里是在联合索引里判断还是回到主键索引中判断呢?

- 在MySQL5.6以前, 只能从主键开始一个个回表来比对其他条件
- 而MySQL5.6以后, 索引下推优化可以在联合索引遍历过程中, 对所有联合索引中包含的字段先做判断, 直接过滤掉不满足条件的记录, 减少回表次数

### 索引区分度

建立索引时字段顺序对索引效率也有很大影响, 越靠前的字段被用于索引过滤的概率越高, 所以区分度大的字段需要排在前面.区分度就是某个字段不同值的个数/表的总行数

## 索引的适用性

索引最大的好处是提高查询速度, 但索引也是有缺点的, 比如
- 需要占用物理空间, 数量约大, 占用空间越大
- 创建索引和维护索引要耗费时间, 随着数据量增大开销增大
- 降低表的增删改效率, 每次增改索引, B+数为了维护索引的有序性, 都需要进行动态维护
### 什么时候适用索引

- 字段有唯一性, 如何商品编码
- 常用于WHERE查询条件的字段, 这样能够提高整个表的查询, 如果查询条件不是一个字段, 可以建立联合索引
- 常用于GROUP BY 和 ORDER BY的字段

### 什么时候不适用索引

- WHERE条件, GROUP BY, ORDER BY里用不到的字段, 索引的价值是快速定位, 如果不需要定位则不用索引
- 字段中存在大量重复数据, 不需要索引, 区分度太低
- 表数据太少
- 检查更新的字段

## 索引优化

### 前缀索引优化

使用某个字段中字符串的前几个字符建立索引
前缀索引可以有效减少索引字段的大小, 增加一个索引页中存储的 索引值, 有效提高索引的查询速度.
不过前缀索引有一定的局限性, 如ORDER BY就无法使用前缀索引, 无法前缀索引用作覆盖索引
### 覆盖索引优化

覆盖索引是指SQL中query的所有字段, 在索引B+Tree的叶子节点上都能找得到的那些索引, 从二级索引中查询得到记录, 而不需要通过聚簇索引回表得到, 就可以避免回表操作
也就是通过需要query的字段建立联合索引来减少回表的IO次数
### 主键索引优化

- 主键索引默认设置为自增的, 叶子节点的各个数据是按主键顺序存放的, 当有一条新的数据插入时, 数据库会根据主键将其插入到对应的叶子节点中
- 如果我们使用自增主键, 那么插入新的数据时, 不需要移动已有数据, 插入效率更高
- 如果使用非自增的主键, 插入的位置是随机的, 如果是在页的中间, 就需要移动现有的数据, 甚至出现页分裂情况, 将数据从一个页面移动到另一个页面, 这样可能产生大量的内存碎片, 导致索引结构不紧凑, 影响查询效率
- 另外, 主键字段的长度越小, 二级索引的叶子节点越小, 约节省空间
### 索引不为空

为了更好的利用索引, 索引列要设置为NOT NULL约束, 原因如下:
- 索引列存在NULL会导致优化器在做索引选择时更加复杂, 难以优化
- NULL是一个没有意义的值, 但是却占用了存储空间
### 防止索引失效

创建了索引不代表查询时一定会使用索引, 需要避免写出索引失效的查询语句
常见情况如下
- 包含左匹配的模糊查询
- 在查询条件中对索引列做了计算,函数,类型转换
- 不满足最左匹配
- 在WHERE子句中, 如果OR前的条件是索引列, 而OR后的条件不是, 那么索引会失效

### 执行计划

执行计划中的参数
- possible_keys 字段表示可能用到的索引；
- key 字段表示实际用的索引，如果这一项为 NULL，说明没有使用索引；
- key_len 表示索引的长度；
- rows 表示扫描的数据行数。
- type 表示数据扫描类型，我们需要重点看这个。

常见扫描类型的**执行效率从低到高的顺序为**：
- All（全表扫描）；
- index（全索引扫描）；
- range（索引范围扫描）；
- ref（非唯一索引扫描）；
- eq_ref（唯一索引扫描）；
- const（结果只有一条的主键或唯一索引扫描）。

执行结果extra
这里说几个重要的参考指标：

- Using filesort ：当查询语句中包含 group by 操作，而且无法利用索引完成排序操作的时候， 这时不得不选择相应的排序算法进行，甚至可能会通过文件排序，效率是很低的，所以要避免这种问题的出现。
- Using temporary：使了用临时表保存中间结果，MySQL 在对查询结果排序时使用临时表，常见于排序 order by 和分组查询 group by。效率低，要避免这种问题的出现。
- Using index：所需数据只需在索引即可全部获得，不须要再到表中取数据，也就是使用了覆盖索引，避免了回表操作，效率不错
