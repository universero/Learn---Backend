## 概述

HTTP (HyperText Transfer Protocol, 超文本传输协议), 是一个客户端-服务器协议，用于在Web上传输数据。

- 请求方: user agent 或 proxy
-  响应方: Web服务器

## 特性 

- 简约
	- HTTP简约易读，信息是明文
	- 但也导致了不安全，可能被窃听和篡改。但通过引入SSL/TLS层，可以解决
- 可扩展
	- HTTP/1.0 引入的HTTP标头使得协议可以扩展
- 无状态，有会话
	- 同一个连接中两个执行成功的请求之间没有关系
	- 借助Cookie就可使用有状态的会话，使得请求共享上下文
- 有链接
	- 底层由TCP实现传输

## 版本

- HTTP/0.9
	- 单行指令，如`GET /page.html`, 响应只包含文档本身

- HTTP/1.0
	- 构建可扩展性，引入版本信息，header，状态码和请求方法等

- HTTP/1.1 - 主流的HTTP协议版本
	- 特性
		- 长连接：当客户端和服务器任意一端没有明确提出断开连接则TCP保持连接状态，连接复用减少了建立连接的开销
		- 管道技术：一个TCP连接中可以发送多个请求，但服务器必须按照接受请求的顺序处理响应。管道解决了请求的队头阻塞，但是没有解决响应的队头阻塞。HTTP/1.1不是默认开启的，浏览器基本不支持
	
	- 遗留问题
		- 头部冗余：每次都需要发送一定的header
		- 队头阻塞：响应需要按序处理
		- 请求优先级控制：没有优先级控制
		- 服务器无法主动推送：服务器只能被动响应

- HTTP/2
	- 头部压缩：HPACK压缩算法对请求和响应头部进行压缩，减少传输的头部数据量，降低延迟。
		- HPACK算法压缩头部包含三个部分
			- 静态字典: 为高频的header建立一张静态表嵌入在协议中，用较小的索引表示重复的字符串，再用Huffman编码压缩数据
			- 动态字典: 在一个连接上动态生成的表，用索引维护传输完全相同的HTTP头。但是太多会导致内存占用过大, 由http2_max_requests配置
			- Huffman编码: 

	- 二进制帧：将数据分割成二进制帧传输，分为头信息帧和数据帧，增加传输效率

	- 并发传输(多路复用): 引入Stream机制，多个Stream复用一条TCP连接，针对不同的HTTP请求用不同的Stream ID区分，接收端可以通过Stream ID有序组装HTTP消息。可以并发进行多条请求-响应
		- HTTP/1.1基于请求-响应模型，同一个连接中完成一个事务才能处理下一个事务。
		- HTTP/2不同Stream的帧可以乱序发送，而且可以通过帧的控制位实现优先级控制

	- 服务器推送：服务器可以对客户端的一个请求发送多个响应，实现额外推送资源，而无需客户端明确的请求。
		- 客户端发送的请求必须是奇数的StreamID，服务器的主动推送必须是偶数的StreamID，通过PUSH_PROMISE帧传输HTTP头部，并通过帧中的Promised StreamID告知客户端会在Stream中发送包体
	
	- 问题
		- 队头阻塞：仍会有队头阻塞，不过是发生在传输层。TCP的数据包没有完全到达时，不会传递给应用层。
		- TCP与TLS的握手时延
		- 网络迁移需要重新建立连接

- HTTP/3
	- 将TCP换成了UDP，基于QUIC协议，有如下特点
		- 零RTT连接建立：QUIC允许首次连接时进行零往返时间连接建立，从而减少了连接延迟，加快了页面加载速度。
			- TCP和TLS分层，分别属于传输层和表示层，需要分批次握手建连。
			- QUIC协议包含TLS1.3，只需要一个RTT就能同时完成建连和密钥协商。甚至第二次连接时，数据包和握手信息可以同时发送实现0-RTT
		- 无队头阻塞：QUIC使用UDP协议传输数据，一个连接上的多个Stream之间没有依赖，一个Stream丢包不影响其他的，没有TCP队头阻塞。
		- 连接迁移：QUIC允许在网络切换时，将连接迁移到新的IP地址，从而减少了中断时间
			- TCP通过源IP、源端口，目的IP，目的端口四元组确定TCP连接
			- QUIC通过连接ID标记两个通信端点，网络切换虽然IP变化，但是只要保有上下就不需要重连
		- 向前纠错：每个数据包中除了本身的内容，还包括了其他数据包的数据，少量的丢包通过其他包的冗余数据直接组装而无需重传。牺牲单个数据包大小上限，减少重传次数
		- 额外单向流：
			- QPACK Encoder Stream：将字典传输给对方，同步QPACK的字典
			- QPACK Decoder Stream：响应，告知已成功同步字典
