MQ(message queue), 用于上下游解耦的队列, 具备接收数据, 发送数据, 存储数据等功能
## 作用

- 高并发的流量削峰
- 应用解耦
- 异步处理
- 分布式事务
- 数据分发

## 常见的MQ

- ActiveMQ
	- 优点: 单机万级吞吐量, ms级时效性, 可用性高, 基于主从架构实现高可用, 消息可靠性高
	- 缺点: 社区对ActiveMQ的维护越来越少, 高吞吐量场景较少使用
- Kafka
	- 优点: 性能卓越, 吞吐量高, 单机写入TPS约在百万条/s, ms级时效, 可用性非常高; kafka是分布式的, 一个数据多个副本, 少数机器宕机不会导致服务不可用与数据丢失, 消费者采用Pull方式获取消息, 消息有序, 通过控制能保证所有消息被消费且仅被消费一次; 有优秀的第三方Kafka web管理界面Kafka-Manager, 在日志领域较为成熟
	- 缺点: 单机超过64个队列, Load会发生明显的飙高现象, 队列越多Load越高, 发送消息响应时间越长; 使用短轮询的方式, 实时性取决于轮询间隔时间, 消费失败不支持重试; 支持消息顺序, 但是一台代理宕机后, 就会产生消息乱序, 社区更新较慢;
	- 场景: 主要特点是基于Pull的模式来处理消息消费, 追去高吞吐量, 一开始的目的是日志收集和传输, 适合产生大量数据的互联网服务的数据收集业务.
- RocketMQ
	- 优点: 单机吞吐量十万级, 可用性高, 采用分布式架构, 消息丢失率低, MQ功能完善, 扩展性好, 支持10亿级别的消息堆积, 不会因为堆积导致性能下降
	- 缺点: 支持的客户端语言不多, 目前是Java以及C++, 且C++不成熟, 社区活跃度一般, 没有在MQ核心中实现JMS等接口, 不利于系统迁移
	- 场景: Java实现; 适用于金融互联网, 对于电商的订单扣款等可靠性要求很高的场景, RoketMQ在稳定性上更强
- RabbitMQ
	- 优点: 在AMQP协议基础上开发的, 由于erlang语言的高并发特性, 性能较好, 吞吐量达到万级, 功能完备, 支持多种语言, 社区活跃度高
	- 缺点: 商业版需要收费, 学习成本较高
	- 场景: 微秒级时效, 社区活跃度高, 适用于中小型公司, 数据量没有非常大的场景

## 消息队列协议

> 为什么消息中间件不使用http协议?
> 因为http协议的报文头等部分过于复杂, 加解密, 状态码等功能对于消息中间件来说过于冗余, 消息只负责数据的传递, 存储, 分发, 追求高性能, 简洁
> 且http大部分都是短链接, 一个请求到响应的过程中可能会中断, 中断以后就不会执行持久化, 造成请求丢失; 但是消息是一个长时间获取的过程, 出现问题和故障需要持久化

- AMQP协议
	- 统一消息服务的应用层标准高级消息队列协议
	- 分布式事务支持、消息的持久化支持、高性能和高可靠的消息处理优势
	- 如RabbitMQ、ActiveMQ
- MQTI协议
	- 基于发布/订阅的轻量级通信协议, 基于TCP/IP协议
	- 轻量、简单、传输快、不支持事务、没有持久化设计
	- 适用于计算能力有限, 低带宽, 网络不稳定场景
	- RabbitMQ和ActiveMQ都支持的默认关闭
- OpenMessage协议
	- 结构简单, 解析速度快, 支持事务和持久化设计
- Kafka协议
	- 基于TCP/IP协议, 通过长度来划分消息, 结构简单, 解析速度快, 无事务支持, 有持久化设计

## 消息队列持久化

吃就换简单来说就是能将数据存入磁盘, 而不是存在内存中随服务器重启而丢失. 常见的MQ都是存储在文件中, 只有ActiveMQ可以存储在数据库中

|      | ActiveMQ | RabbitMQ | Kafka | RocketMQ |
| ---- | -------- | -------- | ----- | -------- |
| 发布订阅 | 支持       | 支持       | 支持    | 支持       |
| 轮询分发 | 支持       | 支持       | 支持    | -        |
| 公平分发 | /        | 支持       | 支持    | -        |
| 重发   | 支持       | 支持       | /     | 支持       |
| 消息拉取 | /        | 支持       | 支持    | 支持       |
